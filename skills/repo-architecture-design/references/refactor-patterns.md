# 常见重构手法目录

每种手法讲四件事:识别信号、做法、代价、什么时候**不该**用。最后一条最关键 —— 手法本身没有对错,只有匹配不匹配。

## 1. 拆上帝对象

- **信号**:一个类几百行,同时管界面、业务、配置、线程、状态;改动它时经常只碰其中一小段,却要考虑全局。
- **做法**:按**变化原因**拆,不按代码长度拆。每拆出一个类,先问"它会因为什么而变" —— 答案不同的才值得分开。
- **代价**:引入跨类调用与信号回调;原先一个文件里一眼能看完的东西,现在要跳几个文件。
- **不该用**:类虽然长,但只有一个变化原因(纯数据表、线性的流程脚本)。这种情况拆了只会让人更难读。

## 2. 提取类

- **信号**:一部分字段与几个方法总是成组出现,和类里其它内容几乎不交互。
- **做法**:把这组字段与方法搬进新类,原类持有一个引用。
- **代价**:多一层转发;若组内方法与原类耦合紧密,会牵扯出大量参数传递。
- **不该用**:这组方法只被调用一两次、且没有独立变化的前景。

## 3. 提取值对象

- **信号**:同一个数据组合(如一段路径加名称、一组评估字段)以裸 `dict` 或元组的形式在多个层之间传来传去,每处都得记住键名。
- **做法**:定义一个小类,把字段与校验、序列化收进去;层间传递这个类型。
- **代价**:需要一处反序列化逻辑;跨语言或跨进程边界时可能不适用。
- **不该用**:只在单个函数内部临时用一下的字典,没必要建类。

## 4. 依赖倒置 / 引入端口

- **信号**:业务逻辑直接依赖外部 SDK 或数据库,导致没法脱离它们做测试。
- **做法**:在业务侧定义接口,由外层提供实现,构造时注入。
- **代价**:多一层间接,阅读时要跳一次。
- **不该用**:**只有一个实现、且短期内不会替换**时不要引入。这条最常被滥用 —— 判断标准见 `over-engineering.md` 的抽象准入规则。

## 5. 恢复单向分层

- **信号**:底层的类反过来引用上层(业务模块 import 界面模块);依赖图里出现环。
- **做法**:把上层需要的能力下沉为接口或回调,让依赖重新单向。
- **代价**:可能需要挪动代码位置,并调整若干构造调用。
- **不该用**:两侧本来就属于同一层、只是文件还没归位时,先移动文件比先抽接口更划算。

## 6. 消除重复

- **信号**:同样一段逻辑在三处以上出现,且改动时总要同步修改。
- **做法**:提取成一个函数或基类,调用方改为调用它。
- **代价**:抽象可能过早固化;两处相似但将来会分道扬镳的代码被强行合并,日后要拆。
- **不该用**:只有两处且差异明显、或两处仅仅是"看起来像"的场合。**三次法则**:到第三次再抽。

## 7. 参数对象

- **信号**:某个函数参数超过四五个,调用方经常传错顺序。
- **做法**:把相关参数收进一个数据类。
- **代价**:多一个类型定义;简单场景下反而啰嗦。
- **不该用**:参数虽然多但语义无关,硬凑成一个对象会更难懂。

## 8. 用策略替换条件分支

- **信号**:同一个函数里出现三个以上并列分支,且还在持续增长。
- **做法**:每个分支提取成一个类,用映射表或注册表按条件选取。
- **代价**:原来一眼看完的 `if-elif` 被拆散到多个文件。
- **不该用**:分支数量固定、逻辑各只有两行 —— 一个 `if-elif` 更清楚。**不要为了消灭 if 而引入十行代码。**

## 9. 组合根(Composition Root)

- **信号**:`new` 散落在各处,想换一个实现要在十几个文件里找。
- **做法**:把对象创建集中到一个入口,其余类只接受注入的依赖。
- **代价**:入口文件会变长,依赖关系需要靠约定维持。
- **不该用**:项目只有两三个类、依赖关系一眼可见时不必强求。

## 10. 统一异常类型

- **信号**:同一类失败在不同层里被反复 `except Exception` 包装,消息格式各不相同。
- **做法**:定义项目自己的异常类型,在边界处统一转换一次。
- **代价**:需要一层映射;调用方要按新类型调整捕获。
- **不该用**:本来就在用标准异常语义清晰的场合,不必再包一层。

## 11. 配置集中

- **信号**:同一个阈值或路径在多处硬编码,改一次要全局搜索。
- **做法**:集中到一个配置类或配置文件,其余地方引用它。
- **代价**:读代码时要多跳一次才能看到实际值。
- **不该用**:只在一个地方用一次的字面量 —— 集中反而增加跳转。**前提是"多处"**,不是"所有"。

## 12. 拆线程与异步边界

- **信号**:耗时操作直接在界面线程里跑,或者跨线程直接改共享状态。
- **做法**:把耗时逻辑挪到独立的执行单元,用消息/信号回传结果。
- **代价**:引入异步复杂度与竞态风险(抑制标志、取消、生命周期)。
- **不该用**:操作用时在肉眼无感的量级(几十毫秒),拆了只是徒增复杂度。

## 怎么选手法

1. 先按纲领里的「重构方向」定痛点的优先级;
2. 每选一个手法,回到 `over-engineering.md` 过一遍量化守门;
3. 被否掉的手法写进报告的否决清单,附理由。
