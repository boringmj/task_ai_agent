# 访谈清单:背景优先

访谈分两轮。第一轮只问背景,第二轮按背景自适应追问。理由很简单:**技术选型、代码风格、预期规模这三组问题的答案,大部分能从背景推出来。** 背景问在前面,后面的问题就能自然收窄。

## 第一轮:背景七组

一次问一组,每组给候选让用户挑。五到七问就能把七组覆盖完。

| 组 | 要问什么 | 常见候选 | 它决定什么 |
| --- | --- | --- | --- |
| ① 项目性质与去向 | 这是什么东西?将来要交付或商业分发吗? | 内部工具 / 教学示例 / 自用脚本 / 对外产品 / 开源项目 / 基础库 | 工程完备度的档次;许可证约束(如 GPL 组件能否用) |
| ② 团队与维护者 | 谁来维护?几个人?熟悉目标技术吗?有专职运维吗? | 只有我自己 / 两三人小组 / 有专职运维 / 会频繁交接 | **架构复杂度的上限** —— 单人维护上微服务是灾难 |
| ③ 生命周期与阶段 | 现在处于什么阶段?预期还会活多久? | 原型验证 / MVP / 已上线 / 长期维护 / 快下线了 | 值不值得投入测试、分层与文档 |
| ④ 规模与增长预期 | 现在多大?会涨吗?涨到多少? | 稳定不变 / 缓慢增长 / 预计快速增长 / 完全不确定 | 要不要预留扩展点 |
| ⑤ 运行与部署环境 | 跑在哪?怎么部署?网络受限或离线吗? | 自己电脑 / 内网服务器 / 公有云 / 客户机器(可能离线) | 依赖选择、打包方式、能不能用外部服务 |
| ⑥ 硬约束 | 有什么必须遵守的规矩? | 合规审计 / 数据不出境 / 许可证限制 / 采购预算 / 必须兼容旧平台或旧版本 | **否决项,不是偏好项** |
| ⑦ 历史与动因 | 为什么现在要重构?有什么必须保留?那些看着别扭的代码是不是在绕某个坑? | 加不动功能了 / 性能问题 / 换人接手 / 代码看不懂 / 合规要求 | 重构的目标与禁区 |

第 ⑦ 组最容易被漏,也最贵。很多丑代码不是水平问题,是在绕一个已修复的 bug、一个客户的特例、或一个平台的怪癖。**不问清楚就顺手优化掉,等于把踩过的坑重新踩一遍。**

## 背景到选型的映射

这张表是「为什么要问背景」的答案 —— 每一条背景都挂着一条会改变方案的推论。没有这张表,问背景就退化成走过场。

| 背景事实 | 直接得出的结论 |
| --- | --- |
| 单人维护、没有运维 | 单体优先;不引入需要长期运维的中间件 |
| 有商业分发计划 | GPL 系组件出局(如 PyQt6),换宽松许可替代品(如 PySide6) |
| 面向初学者、代码要给人读 | 选「易读」而非「工程完备」,克制抽象与设计模式 |
| 必须离线部署 | 依赖要能离线打包;排除运行时下载模型、字体、词库的方案 |
| 生命周期不足半年的一次性脚本 | 不做分层、不做测试金字塔、不留扩展点 |
| 有合规审计 | 禁止把数据发给不可控的第三方服务;必须留日志 |
| 预期快速增长、已有多人协作 | 才值得引入分层、接口与自动化测试 |
| 基础库 / 对外 SDK | 接口稳定性 > 内部整洁;改动要考虑外部使用者 |
| 代码要在课堂上逐行讲解 | 文件粒度、命名直白度优先于"工程规范" |

## 第二轮:自适应追问

背景答完再问。**凡是能由背景推出的,不要重复问** —— 比如已经说了"只有我自己维护、没有运维",就不必再问"要不要上消息队列",直接给出建议即可。

### 1. 重构方向

- 这次是**修结构**(拆类、调分层)、**换形态**(改目录组织、换模块边界),还是**只清理**(删死代码、统一风格)?
- 当前最痛的三个点,排个序。
- 这次明确**不做什么**?(范围边界比范围本身更重要)
- 什么时候算成功?怎么验证?

### 2. 技术选型三态表

逐层让用户给「保持 / 升级 / 替换」,并要一句理由。**不要只问"要不要换技术栈"** —— 太粗,用户答不上来,也落不了地。

| 层面 | 现状 | 三态 | 备注 |
| --- | --- | --- | --- |
| 语言与版本 | | 保持 / 升级 / 替换 | 如 Python 3.9 → 3.12 |
| 核心框架 | | | |
| 关键第三方依赖 | | | 逐个列,别打包成一句 |
| 构建 / 打包方式 | | | 如 venv、PyInstaller、Docker |
| 测试框架 | | | 从无到有也算 |
| 格式化与 lint | | | |
| 日志与错误上报 | | | |
| 配置与密钥管理 | | | |

每一项的「替换」都要附上迁移代价 —— 用户才可能做出理性取舍。

### 3. 代码风格

这些必须问,而且必须问具体:

- 命名约定(类/函数/常量/文件名的大小写与分隔符)
- **文件粒度**:一个文件一个类、一个模块多个类,还是按功能打包?
- 目录扁平度:允许几层?按类型分还是按功能分?
- 注释语言与密度:中文还是英文?只在必要处还是逐函数?
- 类型注解:强制、可选、还是不要?
- 错误处理风格:抛异常、返回错误码,还是 Result 类型?
- 是否引入异步 / 并发?

### 4. 规模与预算

- 目标文件数与类数的**数量级**(要量级,不要精确值)。
- 本次改动的预算上限:时间、行数、可接受的停机。
- 是否允许新增第三方依赖?
- 是否需要保持对外兼容(接口、数据格式、命令行参数)?

## 提问技巧

- **给候选,别开放式。** 问"是内部工具、对外产品还是教学示例",比问"能介绍下项目吗"有效得多。
- **每轮五到七问,不要三十问。** 一口气问完,用户会敷衍。
- **别问用户答不上来的。** "你希望几个类"这种问题应该由你给建议,让用户确认。
- **允许「不知道」。** 但不知道不等于随便定 —— 见下一节。
- **背景优先。** 每问完一组,回去检查后面哪些问题已经不必问了。

## 用户不回答的时候

**不许默默替他拍板一个方便的背景** —— 这是本技能最严重的错误。

正确做法:

1. 把没答的项写进纲领的「显式假设」小节,逐条注明「**推断**」。
2. 对影响大的假设(技术选型、兼容性、合规)单独标出,请用户在纲领上确认。
3. 如果关键背景缺失且无法推断,就**停下来再说一次** —— 宁可多问一轮,也不要基于猜测的结构改代码。
