# Go/No-Go 评估

迁移的成本几乎总被低估,收益几乎总被高估。这一步的作用就是在写任何方案之前,先把这笔账算清楚。

结论必须是三选一,不允许"先干起来再说":

- **值得迁** —— 收益明确、成本可承受、风险有对策。
- **有条件迁** —— 可以做,但必须先满足若干前置条件(逐条列出)。
- **不建议迁** —— 说明理由,并给出替代方案。

## 四个评估维度

### 一、收益(必须具体、可测)

逐条写,写不出数字的条目不算收益:

- 成本下降多少?(服务器费用、授权费、人力)
- 性能提升多少?当前瓶颈具体在哪?
- 是否满足某项合规或审计要求?(要指出是哪一条)
- 是否解除供应商锁定?锁定的实际代价有多大?
- 团队技能是否更匹配?能不能招到人?

反例:「迁到云上更现代」「微服务是趋势」—— 这些不是收益,是偏好。写进评估时请直接剔除。

### 二、成本

- **人力**:人月估算,注明依据(比照类似项目或按模块拆)。
- **停机窗口**:需要多长?能不能接受?
- **双跑期成本**:新旧并行期间的资源与人力。
- **学习曲线**:团队掌握新栈需要多久?
- **隐性成本**:数据迁移、测试重建、文档重写、培训、旧系统维护期延长。

经验法则:**实际耗时通常是乐观估算的两到三倍**。评估时用这个倍数再算一次。

### 三、风险

| 风险 | 触发条件 | 影响 | 对策 |
| --- | --- | --- | --- |
| 数据丢失或不一致 | | | |
| 外部集成断裂 | | | |
| 回滚不可行 | | | |
| 关键人依赖 | | | |
| 期限压力导致跳步 | | | |

### 四、替代方案(这一节不能省)

- **不迁**:优化现有系统能否解决?需要多少成本?
- **少迁**:只迁其中一部分(如只迁数据层)是否够?
- **换路径**:有没有成本更低的方式达成同一目标?

把替代方案和迁移方案并列摆出来,用户才可能做出理性选择。**只给一条路的评估不叫评估。**

## 输出格式

| 维度 | 结论 |
| --- | --- |
| 迁移动因 | <用户给出的原始诉求> |
| 可测收益 | <逐条,带数字> |
| 成本估算 | <人月 / 停机 / 双跑期 / 隐性成本> |
| 主要风险 | <按上表摘要> |
| 替代方案 | <不迁 / 少迁 / 换路径的结论与代价> |
| **综合结论** | **值得迁 / 有条件迁 / 不建议迁** |
| 前置条件 | <「有条件迁」时逐条列出> |

给出建议后**由用户拍板**,不要替用户决定。若用户坚持迁移而评估结论为否,记录分歧后按其决定继续 —— 但把风险写进报告。
