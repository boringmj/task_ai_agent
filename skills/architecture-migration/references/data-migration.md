# 数据迁移

数据迁移常常决定整个迁移方案的可行性 —— 代码搬完只要几天,数据对不上能拖上几个月。所以它在流程里是独立的一步,不是收尾工作。

## 一、先盘点

| 项 | 要查清什么 |
| --- | --- |
| 数据分布 | 关系库、文件系统、对象存储、缓存、消息队列里的积压 |
| 体量 | 行数、占用空间、日增长量 |
| 使用方 | 谁在读、谁在写、有没有遗留的直接连库程序 |
| 敏感度 | 是否含个人信息;迁移是否需要脱敏或额外授权 |
| 生命周期 | 哪些是历史归档(可以不迁)、哪些是活跃数据 |

容易漏的:临时表、定时任务产物、报表缓存、日志里被当作数据用的内容。

## 二、结构映射

产出一张映射表,逐字段确认:

| 旧结构 | 新结构 | 转换规则 | 备注 |
| --- | --- | --- | --- |
| | | 直接映射 / 拆分 / 合并 / 计算 | 无法自动映射的单独标出 |

必须人工处理的几类差异:

- **类型差异**:精度、长度、整数溢出。
- **空值语义**:旧库用空串、新库用 `NULL`(或反之),映射错会静默产生脏数据。
- **时间与时区**:存的是本地时间还是 UTC;夏令时。
- **编码与排序规则**:字符集、大小写敏感性、排序规则差异会影响唯一键。
- **自增主键**:两套序列如何避免冲突。

## 三、迁移方式

| 方式 | 适用 | 代价 |
| --- | --- | --- |
| 全量一次性 | 体量小、可停机 | 需要停机窗口 |
| 全量 + 增量追赶 | 体量大、停机窗口短 | 需记录变更点(时间戳或 CDC) |
| 双写过渡 | 不能停机 | 一致性风险,需补偿与对账 |

增量方案要明确:**变更点怎么记**(时间戳、binlog、触发器),以及**追赶期的写冲突怎么处理**。

## 四、一致性校验

迁移不验收"脚本跑完了",而是验收"对得上":

- **结构校验**:表数、字段、约束、索引是否齐备。
- **数量校验**:行数、分组计数。
- **内容校验**:校验和、或按主键抽样比对。
- **业务级对账**:金额合计、状态分布这类业务口径的核对 —— 最有说服力,也最容易发现结构校验看不出的问题。

**差异处理要有流程**:发现不一致时是停下重迁、逐条修,还是记录后放行?提前定,别临时决定。

## 五、割接窗口

- 列出停机期内的**操作顺序**(停写 → 导出 → 导入 → 校验 → 切流量 → 观察)。
- **至少完整预演一次**,用真实体量或按比例缩放的样本。
- 预演要记录实际耗时,用它来定窗口长度,不要用估算值。
- 为超时准备预案:窗口不够时在哪一步中断、怎么退回。

## 六、失败处理

- **部分成功**:导入到一半失败时,是清空重来还是断点续传?两种都要先想好。
- **幂等性**:重跑一次不能产生重复数据。导入脚本要能重复执行。
- **不可重复的操作**:有些步骤(如发通知、调外部接口)不能重跑,要单独隔离出来。

## 常见坑

- 空值语义不一致,迁移后统计口径全变。
- 时区处理错误,时间字段整体偏移。
- 大表直接 `ALTER` 或全量导入导致锁表,业务超时。
- 外键、唯一约束导致导入顺序敏感,按批量导入时随机失败。
- 迁移脚本自己写错字段对应关系,却因为"跑完了没报错"而被当成成功。
- 旧系统的定时任务仍在写入,迁移期间产生新数据却没被纳入增量。
