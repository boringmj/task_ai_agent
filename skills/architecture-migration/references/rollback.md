# 回滚设计

迁移和重构最大的区别就在这里:重构可以随时停,迁移一旦切过去就得能**退回来**。
回滚方案要在动手之前设计,而不是出事之后临时商量。

## 三条原则

1. **每个阶段都有回滚点。** 没有回滚点的阶段不允许开工。
2. **回滚判据提前定。** 什么指标、到多少、由谁决定,全部事先写清。
3. **不可逆操作单独列出。** 它们要么延后执行,要么先做备份。

## 回滚点清单

每个阶段填一行:

| 阶段 | 回滚动作 | 预计耗时 | 前置条件 | 可逆性 |
| --- | --- | --- | --- | --- |
| <例:切读流量到新库> | <把路由切回旧库> | <5 分钟> | <旧库数据仍为最新,双写尚在> | 完全可逆 |
| <例:停用旧服务> | <重新拉起旧容器> | <30 分钟> | <镜像与配置保留> | 可逆但耗时 |
| <例:删除旧库> | <从备份恢复> | <数小时> | <有当日备份> | 有条件可逆 |

## 不可逆操作

这几类一旦执行就退不回去,必须单独提请用户确认:

- **删除旧数据或旧库**
- **改变数据格式**(新系统写出的数据旧系统读不了)
- **下线旧服务或旧域名**
- **撤销外部集成**(对方系统侧已切换)
- **变更凭据或密钥**

处理方式二选一:

- **延后执行**:主体切换成功后,设一个观察期(几天到几周),期间两套并存,确认无问题再执行。
- **先备份**:确认备份可用,且**实际验证过恢复流程**,而不只是"备份任务显示成功"。

## 回滚判据

提前写清,越具体越好:

| 判据 | 阈值 | 决定人 | 时限 |
| --- | --- | --- | --- |
| 错误率 | <例:连续 10 分钟 > 1%> | | <例:发现后 30 分钟内必须决定> |
| 对账差异 | <例:金额差异 > 0.1%> | | |
| 关键功能不可用 | <例:登录失败> | | |
| 性能劣化 | <例:响应时间翻倍> | | |

**决策时限**尤其重要:拖延本身就是一种风险 —— 拖得越久,旧系统越难回去(数据已分叉、缓存已过期、对方已切换)。

## 演练

- **至少演练一次回滚**,包括数据回滚。
- 演练要记录实际耗时 —— 回滚窗口是硬约束,不能靠估算。
- 演练后更新回滚清单:哪一步比预想的慢、哪一步的手动操作可以脚本化。

## 报告要求

回滚方案要写进迁移报告,并让用户明确确认两件事:

1. 不可逆操作的**执行时机**(立即 / 观察期后 / 由谁触发)。
2. 回滚的**决策人与时限**。
