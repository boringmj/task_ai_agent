# 仓库性能专项审查

输入一个仓库(通常克隆在 `clones/` 下),输出一份中文报告,回答三件事:**已经做了什么优化、哪些是真生效的、瓶颈按什么顺序修**。

适用任何语言与形态:Web 框架、CLI、常驻服务、库。核心方法不依赖具体语言,语言差异只影响"典型优化手段"和"陷阱"两部分,放在 `references/lang-notes.md`。

## 五条铁律

1. **没有实测就不报时间。** 一律用 `每请求 N 次`、`O(n)`、`每查询 1 次 prepare` 这类可复核口径。写毫秒必须来自真实基准,不能由代码推演。
2. **区分「机制存在」与「默认路径生效」。** 缓存代码写了、但默认关闭;开关在两处、实际取的是另一处;只缓存了数据没缓存索引 —— 这些都要判为**收益存疑**,并写清为什么。
3. **先分运行模式。** 短生命周期(每请求一个进程,如 FPM/CGI/CLI)与长生命周期(常驻进程,如 Swoole/Node/JVM/Go 服务)的开销结构完全不同,必须分开算,不能混着说"每请求开销"。
4. **按「出现频率 × 单次成本」排序**,不按代码行数、不按主观印象。一个 1000 行只跑一次的函数不重要,一行跑 N 次的反射才重要。
5. **逐条标注【确认】与【推测】。** 读代码能定的是确认;份额占比、真实耗时属推测,必须写"需压测验证"。

## 步骤

### 1. 摸清形态(先别读代码)

- 读 `README*`、构建/依赖清单(`composer.json`/`package.json`/`go.mod`/`pyproject.toml`)、入口文件,确定:**语言与版本、运行模式、是否常驻、有没有预热/编译步骤、是框架还是应用**。
- 看目录规模:哪些目录占大头。占比最高的两三个目录就是重点,其余抽样。
- 找性能相关的显式设计:缓存目录、`*cache*`、`*compile*`、`*pool*`、`benchmark`、`perf`、`worker`。**先建立"它自称做了什么优化"的列表**,后面逐条验证,而不是从零找问题。

### 2. 机器扫热点

```bash
python scripts/scan_hotspots.py clones/<仓库> --top 30
```

脚本做的是**启发式**统计,给的是候选清单,不是结论:函数长度与分支数、循环体内的 IO/查询/反射/序列化调用、疑似 N+1、进程级可变状态、缓存 API 的调用点分布。

先只看摘要与 top 列表,**不要**把 JSON 全量读进上下文;需要细节时按文件行号定点读。

脚本是**启发式**,有明确的已知局限,别把它的输出当结论:

- 函数边界靠正则 + 括号/缩进配对,遇到宏、匿名类、模板字符串会偏;
- "循环里的重操作"只认直接调用;**通过自定义方法间接访问 DB/IO 的**,它只在同一文件内追一层(标 `indirect:方法名`),跨文件的 N+1 需要人工追;
- 静态状态只认"可变容器/惰性单例"形态,常量式静态属性不算;
- 不区分数据规模,命中的循环可能只跑 1 次。

用法:`python scripts/scan_hotspots.py clones/<仓库> --top 30 --json reports/<仓库名>/perf/scan.json`(脚本路径相对技能目录,不要写绝对挂载路径;产物路径相对工作区)。

### 3. 逐层过清单

按 `references/checklist.md` 走一遍。它按**开销来源**分层,每层给"该看什么"和"常见误判"。语言特定手段与陷阱查 `references/lang-notes.md`(目前覆盖 PHP / Python / JS-TS / Java-Kotlin / Go / Rust / C#;其它语言只有通用层,报告里要说明)。

原则:**只读决定开销的那几行**,不要通读整个仓库。每个结论都必须能落到 `文件:行号`。

### 4. 分模式算固定开销

用 `references/runtime-modes.md` 的两张表分别算:

- **短生命周期**:一次请求从进程启动到响应结束,哪些步骤每次重做?引导、配置装载、路由构建、依赖注入装配、连接建立。
- **长生命周期**:预热之后每请求还剩什么?有没有"做了常驻却每请求重建对象"的地方?请求间清理(`release*`/`reset`/上下文销毁)本身的开销有多大?

同一项在两个模式下的结论经常相反(连接池在短生命周期下几乎无收益,在常驻下收益很大),**不要合并成一句**。

### 5. 出报告

按 `assets/report-template.md` 的结构写,落到 `reports/<仓库名>/perf/performance-review.md`(目标不是仓库时,用它的名字代替 `<仓库名>`)。必须包含:

- 结论摘要:做得好 / 做得不够 / 最大瓶颈(各 3~5 条);
- 已做优化清单表,每条标**真有效**或**收益存疑**,存疑的写原因;
- 问题清单,分严重/中等/轻微,每条带机制与量级口径;
- 分模式开销分析;
- **覆盖范围与盲区**:哪些文件、哪些层没看,哪些结论需要压测才能定。

交出去之前自查一遍(这几条最容易失守):

- 每条问题都能指到 `文件:行号`,没有"某处可能较慢"这种;
- 每条已做优化都给了「真有效 / 收益存疑」,存疑的写了缺哪一条;
- 全文没有未实测的毫秒数;
- 结论标了生效模式,两种模式没有混写;
- 最后有「未覆盖/盲区」,且没有把推断写成事实。

## 判定标准

一条优化算「真有效」,要同时满足:

1. 机制在代码里真实存在(不是只有注释或空壳);
2. 在**默认配置**和**默认调用路径**上生效;
3. 覆盖的是热路径(每请求都走),而不是冷路径(启动一次/异常时才走);
4. 收益没有被别处抵消(例如缓存了路由数据但每请求仍重建索引;省了反射但每请求仍重扫目录)。

缺任何一条,标「收益存疑」并写清缺哪条。全局唯一开关、需要额外命令预热、只在某种模式下生效的,都要在报告里**显式说明生效条件**。

## 常见坑(审查者容易错的地方)

- **把"有缓存"当成"缓存有效"。** 缓存键算错、失效条件过宽、缓存的是元数据而热路径要的是展开后的结构,都会让缓存形同虚设。
- **只看平均,不看最坏。** 线性回退路径(索引 miss 后逐个试)在路由/序列化/依赖解析里极常见,平均看着好,长尾很贵。
- **忽略每请求的一次性小分配。** 单次几百字节 × 每请求几十次,在常驻模式下会变成 GC 压力。
- **把语言运行时当白盒。** OPcache/JIT/GC/逃逸分析的实际行为要靠运行时观测,静态推断只能给"可能"。
- **混淆吞吐与延迟。** 批处理优化能提吞吐但可能加延迟;报告要说明优化的是哪一个。
- **把安全/正确性修复当性能优化。** 反过来也不成立:性能改动不能牺牲请求隔离(常驻模式下尤其危险),发现这类取舍要单独提示。

## 边界

- **不做压测与 profiling**:没有运行环境时,给出的是结构推演与优先顺序,不是性能数字。用户要真实数据,需要另行搭环境跑基准。
- **不做单语句微优化**(把 `array_merge` 换成 `+`、把 `for` 换成 `foreach` 之类),除非它出现在最内层循环且被高频调用。
- **不审安全与代码质量**:发现的问题若属这两类,只在报告末尾列一句"另见其他维度",不展开。
