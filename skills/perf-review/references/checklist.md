# 分层检查清单

按**开销来源**分层,不是按目录。每一层给三样:看什么(定位信号)、怎么判(成立条件)、常见误判。
清单是"该问的问题",不是"该报的问题"——每条都要落到 `文件:行号` 才算数。

## A. 启动与引导

**看什么**:进程启动到能处理第一个请求之间做了什么;有没有预热/编译/预加载步骤,由谁触发。

- 引导代码是否每次请求都重跑(短生命周期模式下这是固定税)。
- 预加载、编译产物、快照文件是否存在;**是否写了但默认不启用**。
- 预热命令是否必须手动执行(CI/部署脚本里有没有这一步)。
- 类/文件扫描是否在启动期做全量遍历,能否换成显式映射或缓存。

**怎么判**:预加载/编译的收益要满足"产物命中 + 不在启动期重新校验"两条。只落盘不命中、或命中前先 stat 一遍,收益会大打折扣。

**常见误判**:把"有 `cache build` 命令"当成"生产环境会用它"。要看默认开关和部署文档。

## B. 配置与环境

**看什么**:配置从哪来(文件/env/远端),解析几次,是否缓存,缓存的生效条件。

- `.env`/配置文件是否每请求解析;解析结果有没有快照。
- 配置缓存是否与"是否存在 env 文件"耦合(存在 env 就关缓存是常见设计)。
- 配置读取是否每次都做深拷贝、递归合并、指纹计算。
- 环境变量读取是否在热路径(每请求 N 次)。

**怎么判**:缓存生效条件要写在**调用点**,不能只写在注释里。开关分散在两处时,以实际生效的那处为准。

**常见误判**:看到 `cache.php` 里有开关就认为生效,没追到引导期实际构造的那个对象。

## C. 请求分发与路由

**看什么**:路由表的构建、索引结构、匹配路径、缓存粒度。

- 路由缓存缓存的是**数据**还是**展开后的索引**?只缓存数据时,每请求仍要 O(N) 重建。
- 静态路径是否走哈希/前缀树(O(1)~O(k)),动态参数是否退化为线性扫描。
- 索引 miss 后的回退路径有多贵(逐个正则试是典型)。
- 路由注册期是否有两两比较(冲突检测),复杂度 O(n²)?
- 路由数量级:几十条无所谓,上千条时 O(N) 每请求就是硬伤。
- 中间件链是否每请求重建对象、是否对不匹配的路径也执行。

**怎么判**:看 `match` 函数里第一条分支命中率和 fallback。**最坏路径比平均路径重要**。

**常见误判**:只测了 demo 的少量路由,没算过 1000 条路由时的行为。

## D. 依赖注入、装配与反射

**看什么**:容器解析一个类要几步;反射结果缓存到哪一级(类、方法、参数);有没有无注解快路径。

- 每次 `get`/`resolve` 是否重新反射构造器、重新扫属性/注解。
- 反射缓存是进程级还是请求级;是否跨请求共享;是否会无限增长。
- 容器元数据是否落盘(编译容器),无注解类是否被记为"空"从而跳过扫描。
- 每请求是否重建容器内核组件(即使绑定表是 COW 复制)。
- 动态代理/装饰器是否每次生成代码或类。
- 单例作用域是否正确:请求级单例在常驻模式下会不会跨请求复用(这是正确性问题,但常被当性能优化做错)。

**怎么判**:区分"反射对象缓存"和"反射结果缓存"。缓存了 `ReflectionClass` 但每次仍遍历所有属性,收益有限。

**常见误判**:把 `setAccessible(true)` 当成开销(PHP 8.1+ 已是空操作)。

## E. 数据访问与 SQL

**看什么**:一条查询从调用到结果映射,中间新建了几个对象、编译了几次、prepare 了几次。

- SQL 是否每次从零编译;编译产物能否按语句结构缓存。
- `prepare` 是否每次调用都执行;有没有语句缓存;模拟预处理开没开(影响缓存收益)。
- 结果集是否 `fetchAll` 全量加载;大结果集能否流式/分页。
- ORM 是否有 N+1(循环里查关联);关联能否预加载。
- 每次查询是否重算连接配置指纹、重新选择连接。
- 连接池:短生命周期下几乎无收益;常驻下才是关键。
- 事务/会话隔离的数据结构是否每查询分配。
- 查询日志/中间件是否在生产也全量开。

**怎么判**:数一条典型查询路径上的对象分配数和 `prepare` 次数。用"每查询 N 个对象 / N 次 prepare"表述。

**常见误判**:把 ORM 的便利层开销算到"框架慢"头上,却没区分是编译、网络往返还是结果映射。

## F. 序列化与编解码

**看什么**:进出边界的数据怎么转:JSON、msgpack、protobuf、PHP serialize、pickle。

- 序列化是否重复做(先转数组再转 JSON、先深拷贝再编码)。
- 大对象是否全量编码;能否流式。
- 反序列化是否带类型校验/白名单(这是安全项,但白名单实现方式也影响性能)。
- 时间/数字/布尔归一化放在赋值期还是渲染期(后者更省)。

**怎么判**:一次请求里同一个数据结构被编码几次。

## G. 模板与渲染

**看什么**:模板是"每次解析"还是"编译成代码";循环体内是否重复解析。

- 有没有模板编译缓存(mtime 失效 + 落盘)。
- 循环内是否为每行新建渲染对象、重新解析整块模板(嵌套循环是乘法级)。
- 正则扫描是否多趟(探测一轮、替换一轮,轮数上限几何)。
- 输出转义是否逐字符处理;能否编译期决定。
- 视图数据是否做了深拷贝。

**怎么判**:渲染成本 ≈ `轮数 × 模板字节数` + `循环行数 × 块字节数`。后者才是大头。

**常见误判**:只看"有没有缓存",没看缓存键是否包含数据(包含数据等于没缓存)。

## H. IO:文件、网络、日志

**看什么**:每请求的 IO 次数,以及是否在循环里。

- 循环体内 `stat`/`file_get_contents`/`include`/HTTP 调用(典型 N+1 IO)。
- 日志是否同步落盘、是否每行 flush、生产级别是否全开。
- 缓存读是否 `include` 一整个文件 vs 读一小段。
- 目录扫描是否在热路径。
- 远程调用是否可并发(串行 N 次 vs 并发)。

**怎么判**:数"每请求 IO 次数"。这个数字比任何时间估算都可靠。

## I. 并发与常驻进程

**看什么**:进程内跨请求复用的东西,以及请求结束时的清理成本。

- 哪些对象是进程级单例(路由表、容器元数据、反射缓存、连接池)。
- 每请求新建的是什么(请求作用域容器、上下文、响应对象)。
- 请求结束清理:遍历哪些表、是否 O(绑定量)、有无泄漏(键无上限增长)。
- 有没有全局锁/协程切换/同步等待。
- 常驻模式下是否仍有"每请求读配置/扫目录/重建索引"。
- 状态隔离是否影响性能取舍(不能为了快牺牲隔离)。

**怎么判**:预热后每请求的分配与清理次数。清理本身可能比它省下的还贵。

**常见误判**:把"常驻"当成自动优化。常驻只省掉引导,热路径的每请求开销一点没少。

## J. 内存与分配

**看什么**:热路径上的大对象、深拷贝、无界缓存。

- 每请求是否复制大数组/大对象(COW 语言里写时复制,但显式拷贝仍贵)。
- 缓存表是否有上限/过期/淘汰(否则是内存泄漏)。
- 结果集是否全量驻留内存。
- 字符串拼接是否在循环里做 O(n²)。

## K. 算法与数据结构

**看什么**:热路径上的复杂度。

- 循环里查数组(线性)→ 能否改成哈希。
- 嵌套循环是否可合并/索引化。
- 排序是否每请求重做(能否缓存排序结果)。
- 正则是否回溯爆炸(用户可控输入进正则尤其注意)。
- 去重/查找是否用错结构(list 当 set 用)。

## 收尾:交叉验证

同一件事从两个角度看,结论会更稳:

- **复杂度视角**(静态):每请求 O(N) 还是 O(1);
- **分配视角**(静态):每请求新建多少对象;
- **IO 视角**(静态):每请求多少次系统调用;
- **实测视角**(如有环境):火焰图/采样,确认前三者的占比。

前三者都是【确认】级的机制判断,第四者是【推测】转【确认】的唯一途径。没有第四者时,报告里必须写明"占比需压测"。
