# 运行模式:两种开销结构

性能结论**必须绑定运行模式**。同一条优化在两种模式下经常得出相反结论,混着说就是错的。

## 先判定属于哪种

| 信号 | 短生命周期 | 长生命周期 |
| --- | --- | --- |
| 进程模型 | 每请求 fork 一个 worker / 每命令一个进程 | 一个进程持续 serve |
| 典型代表 | FPM、CGI、传统 CLI、serverless 函数 | Swoole/RoadRunner/FrankenPHP worker、Node、JVM、Go、.NET 常驻服务 |
| 启动代码 | 每请求执行 | 只执行一次 |
| 请求间状态 | 天然隔离 | 需要显式清理 |
| 连接 | 每请求新建(或持久连接池复用) | 进程内池化 |

判定方式:看入口文件是否包在"循环处理请求"里;看有没有 `worker start` 一类命令;看文档是否提到常驻/预热。

**混合情况很常见**:同一个项目既有 FPM 入口又有 worker 入口。遇到时**两套分别算**,报告里并列,不要取平均。

## 短生命周期:一次请求的固定税

按顺序逐项核对,每项问"每次请求都重做吗?能缓存吗?缓存的生效条件是什么?"

| 步骤 | 是否每请求重做 | 可缓存到什么程度 | 失效条件 |
| --- | --- | --- | --- |
| 语言/框架引导 | 是 | 预加载、OPcache/JIT 预热 | 代码变更 |
| 配置装载 | 是 | 编译快照(注意与 env 文件的耦合) | 配置/env 变更、指纹不符 |
| 路由/清单构建 | 是 | 缓存「数据」还是「索引」是关键差别 | 路由文件变更 |
| 依赖注入装配 | 是 | 元数据缓存 + 反射缓存 | 类变更 |
| 连接建立 | 是 | 持久连接、外部连接池 | 超时、服务端回收 |
| 模板解析 | 是 | 编译成代码 + 落盘 | 模板 mtime |
| 类/文件扫描 | 是 | 显式映射、扫描结果缓存 | 新增文件 |

**关键判断**:缓存格式是"可解释的结构"还是"可直接使用的运行时结构"。前者命中后仍要重建索引/对象,后者才能真正省掉。

## 长生命周期:预热之后还剩什么

| 阶段 | 预期 | 常见反模式 |
| --- | --- | --- |
| 引导 | 只一次 | 每请求重新 `new` 引导对象 |
| 路由表 | 进程级复用 | 每请求重新 import/建索引 |
| 反射与元数据 | 进程级复用 | 每请求新建反射缓存实例 |
| 连接池 | 进程级复用 | 每请求建连接、池却按请求创建 |
| 请求作用域对象 | 每请求新建 | 用进程级单例承载请求数据(越权风险) |
| 响应写出 | 每请求 | 写出后才做的清理拖慢下一个请求 |

**必须检查的三件事**:

1. **"常驻了却没拿到收益"**:进程是常驻的,但热路径上仍有每请求重建——这是最常见的假优化。
2. **请求间清理成本**:遍历多少表、是否 O(绑定量)、键是否无上限增长(泄漏)。
3. **请求隔离**:清理漏了会导致状态串请求。性能上"少清理"看似更快,但这是正确性红线,不能作为优化建议提出。

## 每请求开销的记账方式

用一张表把"每请求做几次"记下来,不写时间:

| 动作 | 每请求次数 | 单次成本形态 | 可否缓存 |
| --- | --- | --- | --- |
| 配置解析 | 1 | O(文件字节数) | 是 |
| 路由索引重建 | 1 | O(N) | 是(需缓存索引) |
| 反射调用 | K(按装配类型数) | O(1)~O(属性数) | 是 |
| SQL 编译 | Q(按查询数) | O(语句复杂度) | 是 |
| `prepare` | Q | 一次网络往返或本地解析 | 视驱动 |
| 结果映射 | R(按行数) | O(R) | 否 |
| 日志写 | L | 同步 IO | 批量/异步 |

这张表就是报告的骨架:**频率列决定优先级,复杂度列决定单次成本**。

## 典型的模式相关结论

- 连接池:短生命周期下几乎无收益(进程活不过一个请求);常驻下是关键优化。
- 持久连接:短生命周期下有用(跨进程复用),但要注意服务端超时与事务残留。
- 预加载/编译:两种模式都有收益,但短生命周期下收益被"每请求仍要校验"稀释。
- 对象池/复用:短生命周期下无意义,常驻下要防"复用了脏对象"。
- 请求作用域单例:短生命周期下天然成立,常驻下必须显式实现,否则是正确性 bug。

## 报告里怎么写

每一条都要标注生效模式:

- 「FPM 下每请求 O(N) 重建索引;worker 模式下 N=0(进程级复用)」
- 「连接池在 FPM 下收益存疑(进程只活一个请求),在 Swoole 下真有效」

不标注模式的性能结论,等于没结论。
