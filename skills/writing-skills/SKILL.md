# 编写技能

技能是**按需加载的说明书** —— 平时只占一行(名字 + 何时使用),需要时才把正文读进来。
所以它适合放"**只在特定场合才用得上的、成体系的**知识与流程",不适合放"任何时候都该遵守的纪律"
(那些属于系统提示词)。

## 目录结构

在项目根的 `skills/` 下建一个目录,目录名就是技能名:

```text
skills/<技能名>/
    SKILL.md          必需
    scripts/          可选:可执行脚本
    references/       可选:按需读进上下文的参考资料
    assets/           可选:产出里要用的文件(模板、图标)
```

`SKILL.md` 必须以一小段 frontmatter 开头,用 `---` 包起来:

```markdown
---
name: <技能名,和目录名一致>
description: <什么时候该用这个技能>
---

# 标题

正文……
```

## description 是关键,要写"什么时候用"

**清单里只显示 name 和 description** —— 模型就是靠这一行判断"现在该不该翻开它"。
所以要写**触发条件**,不是写"这个技能讲什么":

- ✅ 好:当用户要求审阅代码、或改完代码想检查有没有问题时使用。
- ❌ 差:关于代码审阅的说明。 —— 模型看完不知道什么时候该用

措辞上建议用第三人称陈述("……时使用"),而不是祈使句("请使用这个技能……")。

## 边界也要写进 description

模型**加载之前只看得到 description** —— 正文里的"目前只支持 .xlsx"那句,它翻开
之前根本看不到。边界不写在这里,它就会拿这个技能去处理根本不适用的输入,而且
**一路硬撑到出结果**,不会告诉你哪里没覆盖到。

判断标准:**只要有"某些输入处理不了",就写进 description**。

以"解析报表"这个技能为例,两版的差别:

- ❌ 差:当用户要求解析报表文件时使用,支持统计汇总与格式转换。
  —— 用户给个 `.xls`,它照样接下来,做到一半才发现解析不了
- ✅ 好:当用户要求解析报表文件时使用,支持统计汇总与格式转换。**目前只支持
  `.xlsx`**;`.xls` 和 CSV 请另想办法。

什么都能处理的技能(流程类、格式类)不用写这段。

**但只写"不适用于什么",别写"该找谁"。** 在 description 里指名道姓地写「见 xxx 技能」有两个
问题:对方一改名这句就**悄悄过期**(这几天改过两次技能名);而且它把清单撑长,读者要跳过一段
跟自己无关的话才到重点。**只写"不管什么"就够了** —— 模型知道这不是你管的事,自己会去翻别的
技能(清单里都列着)。

要指路就写在**正文**里 —— 翻开之后才需要它,不占清单的地方。

**举例也一样,别点名。** 正文里写「现成的例子见 `xxx` 技能」同样会随对方改名、改内容而失真 ——
而且它比 description 里的指路**更隐蔽**,因为藏在正文中间,重读时不容易留意到。举例就用
**自足的假想例子**(「一个解析报表的技能…」):谁也改不动它,也就永远不会过期。

## markdown 格式有硬要求

技能是给人看的 markdown。格式乱的话用户一打开就是满屏 lint 警告,很影响观感。

**写在工作区里的 markdown 会被自动检查** —— `write_file` / `append_file` / `edit_lines`
写完 `.md` 会顺手 lint 一遍,有问题直接附在返回里;所以**看到提示就当场改掉**,要单独复查用
`check_markdown`。(`skills/` 下的文件在工作区**之外**,工具够不到,那份由用户自己的编辑器
把关 —— 你只负责把内容写对。)

最容易踩的几条(编号是 markdownlint 官方规则号)。**前两条是重灾区**,实测栽得最多:

- **MD032 列表上下都要空一行** —— 最常犯的就是写完"下面几点:"直接接列表。
- **MD036 别拿加粗当标题** —— `**第一步**` 整行加粗、自成一段就算违规;要分小节就写 `###`。
- **MD022 标题上下空一行 / MD031 围栏前后空一行 / MD040 代码块要标语言。**
- **MD041 / MD025** —— 正文第一个非空行是一级标题;且全文**只能有一个** `#`。
- **MD012 / MD009 / MD047** —— 不要连续空行、行尾不要多余空格、结尾留且只留一个换行。
- **MD004** —— 无序列表符号全文统一用 `-`。

## 多层代码块嵌套

写技能时经常要示范含代码块的 markdown,而内层围栏会把外层**提前闭合**,整篇结构就乱了。
办法是**外层用更长的围栏**(外层四个反引号、内层三个)。完整示例与要点见
`references/nested-code-blocks.md`。

## 正文该写什么

写**具体怎么做**:步骤、判断依据、容易踩的坑、判断标准。可以引用工具名(比如
"先 `read_file` 看一眼")—— 技能和工具是配合关系,不是替代关系。

写的时候想清楚:模型**看到这篇正文之后**,行为会有什么不同?答"没什么不同"就不值得存在。

## 依赖要声明在 frontmatter 里,不要只写在正文里

技能的脚本要装包、或者要用别的技能的资源,就在 frontmatter 里声明 —— **机器只读得到这里**,
正文里写再多也只是给人看:

```yaml
requires:                      # 硬依赖:缺一个,这个技能就干不了活
  - package: pyyaml
    reason: 全部规则都写在 rules/*.yaml 里,读不出来就一条都用不上
optional:                      # 可选依赖:缺了只是降级,代价可接受
  - skill: repo-structure-analysis
    reason: 它的 `scripts/scan_repo.py` 能出模块依赖图
    fallback: 自己用 grep 手工摸依赖,慢一些且容易漏掉循环
```

只有 `package`(容器里的 Python 包)和 `skill`(另一个技能)两种 —— 因为它们能被**确切**
回答"装没装"。像「VM 里得有 node」这种宿主查不到的,写进正文,别设成字段。

**硬还是可选,只看一条:缺了它,这个技能还能不能给出一个诚实的结果?** 整个做不了就
`requires`;只是某一步降级、且降级的后果说得清就 `optional`。`optional` 的每一项**必须**
写 `fallback`(自检会拦)—— 写不出一个能接受的下场,它其实就是硬依赖。`reason` 也必写。

**装包之前永远先问用户** —— 装包是**在动用户的环境**,不在"看代码"这个授权范围内。

**最怕的是硬凑**:少了一个包就装作扫全了,用户拿到的是**看着像结论的猜测** —— 比明确说
"这块没查"糟糕得多。加载时怎么把这些告诉模型、几种情况的完整对照、以及一个"该不该降级"
的例子,见 `references/dependencies.md`。

## 别写死路径

正文里提到自己的资源,**只写相对技能目录的路径**(`scripts/foo.py`、`references/bar.md`)。

**绝对路径(`/skills/<技能名>/...`)是明令禁止的**,自检会拦。两个理由:

- **技能是要能搬的。** `/skills` 只是**当前这个宿主**的挂载点 —— 换个人拿去用、换个挂载
  方式,这句话就是错的。写死它就等于把技能和这个项目焊在一起了。
- **它会悄悄过期。** 技能改名、资源挪位置,写死的路径不报错、不失效,只是**指向一个不存在
  的东西**;要等你真的去跑才发现。而相对路径**根本不会过期** —— 位置从来就没被写下来过。

那模型怎么知道真实位置?**加载技能时会给。** `load_skill` 的返回里会把每个资源在容器里的
实际位置列出来,正文说"跑 `scripts/foo.py`",它自己就能对上。

用**别的技能**的资源就加上技能名:`技能名/scripts/x.py` —— 一眼看得出是谁的、能直接核对
文件在不在,而且**位置由依赖声明负责**(所以在 frontmatter 里声明 `skill: 对方`,自检会拦
"用了却没声明")。

## 附带资源

- `scripts/` —— **可以执行而不必读进上下文**。所以重的活(批量处理、格式转换)适合写成脚本,
  让模型只跑它、不读源码。
- `references/` —— 大段参考资料(规范、清单、示例集)。正文里点明"需要时去读哪个",
  而不是把内容整个抄进正文。
- `assets/` —— 产出里要被复制/引用的文件(模板、字体、图片)。

**这些文件是怎么被用到的**:技能目录在工作区**之外**,文件工具够不到它;但它被**只读**
挂载进容器,所以要用 `run_command` / `run_python` 走容器那条路。脚本自己要引用同目录下的
文件(比如 `rules/*.yaml`),**用 `__file__` 往上推** —— 别管容器把它挂在哪儿。只读:
能跑能读、改不了;VM 里看不到。

## 加完之后

技能是**自动发现**的:目录建好、`SKILL.md` 写好,下次启动就会出现在技能清单里,
不需要改任何代码或提示词。可以用 `load_skill("<技能名>")` 验证能不能读出来。

**交出去之前**跑一遍自检:

```bash
python3 scripts/check_skill.py           # 查全部技能
python3 scripts/check_skill.py <技能名>   # 只查一个
```

它查的都是**改名或挪文件之后才会暴露、而且不会报错**的那类问题:

- **写死的路径** —— 正文或脚本里出现 `/skills/<名>/…` 就是错,改成相对路径
- **依赖** —— 字段写全了没有(`reason` 必写,可选依赖还要 `fallback`)、每条能不能
  **单独读懂**(「同上」会被拦:哪几项会出现要到加载时才定,缺席的压根不显示)、
  `skill:` 指的技能在不在、用了人家的资源有没有声明
- **资源引用** —— 正文提到 `scripts/x.py`、`references/y.md`,那些文件是否真的存在
- **frontmatter** —— `name` 与目录名是否一致、`description` 写了没有
- **范围声明** —— description 里有没有交代"处理不了什么"(没写只是提醒,不算错)
- 正文行数是否过长、附带 Python 脚本有没有语法错误

**为什么非要机器查一遍**:这类问题**肉眼扫不出来** —— 资源引用藏在正文中间、脚本里那句
提示藏在几百行代码里,而改名的时候你的眼睛正盯着别处。踩过不止一次,每次都是事后 grep
才发现的。

自检脚本靠 **PyYAML** 读 frontmatter;容器里没装它会**明说「依赖字段这次没查」**,不会假装查过。

**动手写新技能之前**,先看一眼现有的引用关系,能少造一个重复的:

```bash
python3 scripts/check_skill.py --graph
```

它不给图、给**清单** —— 谁引用了谁(分「声明依赖」「用了但没声明」「仅提及」三档)、改某个技能
要同步哪些地方,以及几类值得看一眼的:互相引用(可能是在互相推诿,也可能是真配合,得人看)、
被很多技能引用的枢纽(改它影响面大)、与谁都不往来的孤岛。
