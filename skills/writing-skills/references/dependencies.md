# 技能的依赖

技能能声明两种依赖,**只有两种**:

| 字段 | 含义 | 缺了会怎样 |
| --- | --- | --- |
| `requires` | 硬依赖 | 这个技能干不了活 |
| `optional` | 可选依赖 | 只是降级,代价可接受 |

每项写成一个键值对,`skill` / `pip` 二选一,外加 `reason`;`optional` 还要 `fallback`:

```yaml
requires:
  - pip: pyyaml
    reason: 全部规则都写在 rules/*.yaml 里,读不出来就一条都用不上
optional:
  - pip: dulwich
    reason: git 历史扫描那一步要用
    fallback: 跳过那一步,在报告「未覆盖范围」里写明 git 历史未扫
  - skill: repo-structure-analysis
    reason: "它的 `scripts/scan_repo.py` 能出模块依赖图"
    fallback: 自己用 grep 手工摸依赖,慢一些且容易漏掉循环
```

## 每一项都必须自足 —— 不许写「同上」

**依赖是可插拔、无序的**,不是一段按顺序读下来的文字。而且**哪些项会出现,事先不知道**:
加载时只把「在场」的可选依赖打在模型面前,缺席的那些根本不显示。所以完全可能出现这种情况 ——

```yaml
optional:
  - pip: tree_sitter
    reason: 用它把 PHP 解析成 AST
    fallback: 退回通用扫描器,报告里写明覆盖缺口
  - pip: tree_sitter_php
    reason: 同上            # ← 只有 tree_sitter_php 装了的时候,这行就是孤零零一句
    fallback: 同上
```

装了一半(引擎在、语法定义不在)是完全可能的,那时模型看到的就是**一句没有上文的「同上」**,
它只能猜。**每一条都要能单独拎出来读懂** —— 不引用同级的其他条目,也不引用正文的章节号。

自检会拦这类值(`同上` / `见上` / `如上` / `同前` / 同上所述之类)。

## 为什么只有 `pip` 和 `skill` 两种

因为它们能被**确切**回答"装没装":

- `pip` —— 看容器的包仓库(`.pylibs`)里有没有它。技能脚本跑在容器里,
  所以看的是那一份,不是宿主的 Python。
- `skill` —— 看技能目录在不在。

### `pip` 管到哪儿为止

它查的是**「有没有用 `pip --target` 装进 `.pylibs`」**这一件事,仅此而已。
范围外的**一律不要声明**:

| 什么 | 查得到吗 | 怎么办 |
| --- | --- | --- |
| `pip install --target .pylibs X` 装的包 | 查得到 | 用 `pip:` 声明 |
| 标准库(`json`、`os`…) | 查不到,永远报缺 | **不用声明** —— 本来就不必装 |
| 基础镜像自带的(`pip`、`setuptools`…) | 查不到,永远报缺 | **不用声明** —— 本来就在 |
| npm / composer / gem / apk | 查不到,永远报缺 | 写进**正文**,别设成字段 |
| VM 里(guest)的运行时与包 | 查不到 | 写进**正文** |

后三行要留神:声明了它们**语法上完全合法、自检也放行,但会永远报缺** —— 于是硬依赖
会假警报,让模型停下来告诉你"做不了",而其实跑得起来。

像「VM 里得有 node」「系统里得有 ffmpeg」这类**外部命令**,同理:写进正文里说明,别设成
字段 —— **一个给不出确定答案的检查,比没有检查更危险**:它会说"应该装了吧",然后你在
用到它的那一刻才发现没有。

## 硬还是可选:分界线是「缺失的代价」

判断标准只有一条:**缺了它,这个技能还能不能给出一个诚实的结果?**

- **整个做不了** → `requires`。缺 pyyaml 就一条规则都读不出来 —— 那不叫降级,叫干不了。
- **只是某一步降级,而且降级的后果说得清** → `optional`。少了 dulwich 只是 git 历史那步
  扫不了,其余照常,报告里写明就行。

`optional` 的**每一项都必须写 `fallback`**,自检会拦。这条不是形式主义:

> **"代价可接受"是要被证明的,不是被声称的。** 写不出一个能接受的下场,就说明它其实是硬依赖。

`reason` 同样必写。写不出来的话,多半是你自己也没想清楚它到底是不是必需的。

## 加载时会发生什么

`load_skill` 会把这些自动告诉模型:

| 情况 | 告诉它什么 |
| --- | --- |
| 硬依赖**齐了** | 列出来,确认可以开工 |
| 硬依赖**缺了** | **明确警告** |
| 可选依赖**在场** | 主动说它补上什么、资源在哪 |
| 可选依赖**缺了** | **不提醒** |

两条最要紧的:

**硬依赖缺了,必须停下来。** 加载时会明说三件事:缺了什么、**不要换别的方法硬做**、
把**做不了的是哪一部分**如实告诉用户。模型的本能是"绕过去",而绕出来的东西用户看不出是
残的 —— 那是**看着像结论的猜测**,比明说做不了糟糕得多。

**可选依赖缺了,不提醒。** 它的缺失代价既然是可接受的,就不值得占模型的注意力。但它在场
时**要主动说** —— 让模型知道自己手里的牌比想象的多(可以用那个技能的哪些资源、哪些能力)。

## 装包之前永远先问用户

装包是**在动用户的环境**,不在"看代码"这个授权范围内。把三件事讲清楚,由用户决定:

1. 要装什么、怎么装 —— `pip install --target .pylibs <包>`(装一次持久保留)
2. 装它做什么
3. **不装的后果是什么** —— 正是上面那个 `fallback`

## 一个例子

一个"扫描报表"的技能靠 `pandas` 读 `.xlsx`:

- 声明 `requires: pip: pandas` —— 没有它一个报表都读不了。
- 要是少了它还能读 `.csv`,那就降为 `optional`,并在 `fallback` 里写明"`.xlsx` 读不了、
  `.csv` 还行"。

两种后果,报告的写法完全不同 —— 所以必须写下来。
