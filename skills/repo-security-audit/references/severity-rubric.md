# 严重度与置信度

每条问题都要同时给**严重度**和**置信度**两个判断。前者说"有多坏",后者说"有多确定"。两者独立,不能互相替代。

## 严重度

| 级别 | 判据 | 典型例子 |
| --- | --- | --- |
| critical | 无需认证即可 RCE / 拿到全量核心数据 / 接管云资源;或有明确公开的武器化路径 | 未认证反序列化、SQL 注入直连生产库、云 AK/SK 泄露且有效 |
| high | 需要低门槛前置(登录为普通用户)即可 RCE / 越权访问大量数据 / 绕过认证 | 认证后的命令注入、任意文件上传可执行、IDOR 可拖全量用户、JWT 密钥硬编码 |
| medium | 影响有限,或利用条件苛刻;信息泄露但不含凭据 | 反射型 XSS、SSRF 但限制较多、路径穿越但目录受限、中危组件漏洞 |
| low | 加固类、最佳实践偏离,单独难以利用 | 缺少安全响应头、日志打印非敏感信息、弱算法但非安全敏感场景 |
| info | 提示性,需结合上下文判断 | 调试端点存在但外网不可达、目录浏览但内容公开 |

### 定级时问自己

1. **要前置条件吗?** 无需认证 > 普通用户 > 管理员。
2. **能到多远?** RCE / 数据库 > 单点数据 > 元信息。
3. **影响面多大?** 全部用户 > 单个用户 > 无实际数据。
4. **利用难吗?** 一个请求 > 需要构造 > 需要特定时序 / 竞态。

四条里多数落在最高档,就给高级别。**拿不准时往下取一档**,并在报告里说明理由 —— 虚报高危比漏报一样伤,会让用户对整份报告失去信任。

### 关于组件漏洞

OSV 给的是版本级判断,不反映实际可达性。定级时叠加两个问题:

- 这个库在项目里**真的被调用**了吗?(`grep_files` 搜 import)
- 调用它的路径**对外可达**吗?(框架 / 对外接口高,仅构建工具的依赖低)

对命中但不可达的,降到 low 或 info,并写明"需确认调用路径"。

## 置信度

| 级别 | 含义 | 什么时候用 |
| --- | --- | --- |
| 确认 | 已读代码,看到完整的可控输入 → 危险点,中间无过滤 | 你能引用具体行号说明数据流 |
| 很可能 | 关键环节已确认,但有一处依赖上下文(如某个函数未展开看) | 写清还差哪一环没验证 |
| 待验证 | 命中规则但没读上下文,或依赖运行时配置(环境变量、容器参数、云策略) | 静态扫描看不到的,明确写出来 |
| 存疑 | 疑似,但更可能不是 | 保留在附录,不占正文 |

## 两个维度怎么配合

| | 确认 | 很可能 | 待验证 |
| --- | --- | --- | --- |
| critical / high | **立即修** —— 报告正文最前面 | 优先确认后再修 | 先验证,别急着定论 |
| medium | 排期修 | 排期修 | 观察 |
| low | 顺手修 | 加固建议 | 附录 |

报告正文里,**只写"确认"和"很可能"的**;纯扫描命中还没看过的,统一放进附录并标明"未人工确认"。这样用户一眼就能分清哪些结论可以信。

## 别做的事

- 不写"可能存在 SQL 注入"这种没有判据的模糊结论 —— 要么给出可控性判断,要么说明为什么判不了。
- 不把置信度当免责声明用:写了"很可能"却按 critical 排在最前,等于没说。
- 不把严重度全都写在最高档。分级本身是信息。
