# git 历史里的秘密

## 为什么值得单独扫一遍

攻击者拿到仓库(私有仓库被误设为公开、离职员工的本地副本外流、CI 缓存泄漏),
第一件事就是翻历史。而**删除文件不会让内容消失**:只要提交过,blob 就留在对象库里,
`git log --all --full-history -- path` 就能捞回来。rebase、force-push、reset 也一样 ——
旧对象还在,直到执行 gc 且过了过期时间。

所以:**当前代码干净,不代表仓库干净。**

## 历史里最值钱的三类东西

1. **凭据** —— 被删掉的 `.env`、清过的配置文件、当年硬编码在源码里的 key。
2. **已删除的敏感文件** —— `.env.prod`、`id_rsa`、`*.pem`、数据库导出 `*.sql`、`*.bak`。
3. **旧版本的漏洞代码** —— 某个危险接口"现在删了",但线上跑的旧版本可能还在。

## 怎么扫

```bash
python /skills/repo-security-audit/scripts/scan_git.py \
    /workspace/clones/<仓库> --out /workspace/git-findings-<仓库>.json
```

容器里没有 `git` 命令,脚本用纯 Python 的 `dulwich` 直接读 `.git` 对象库。
可选参数:`--dangling`(扫 rebase / force-push 遗留的不可达对象)、
`--patterns`(连历史代码的危险模式一起扫)、`--max-blobs` / `--max-size` 控规模。

结果里每条都有 `git_status`:

| git_status | 含义 | 意味着什么 |
| --- | --- | --- |
| `deleted` | 这份内容当前分支已经没有了 | **文件删了,秘密没删** —— 优先处理 |
| `changed` | 文件还在,但内容变了 | 旧版本内容泄漏 |
| `dangling` | 没有被任何提交引用 | rebase / force-push 的遗留物 |

## 怎么定级

- 历史里出现过的**凭据**,一律按"已泄露"处理 —— 不管现在删没删,只要 push 过就算泄露。
- 内容已从当前分支删除的,在静态扫描的级别上**提一档**(脚本已自动做)。
- 只是文件名敏感、内容里没有凭据(比如空的 `.env`) → medium,提示清理历史即可。
- 历史里的**漏洞代码**:旧版本仍可能在线运行,按"待确认"处理,写进报告让用户核对线上版本。

## 怎么处置(直接抄进报告的修复建议)

1. **先轮换,再清理 —— 顺序不能反。** 凭据进过历史就当它已泄露,清理历史挽不回已经泄漏的事实。
2. **清理历史**用 `git filter-repo`(推荐)或 BFG:

   ```bash
   git filter-repo --path config/.env --invert-paths
   git filter-repo --replace-text <(echo 'AKIDxxxxxxxx==>***REMOVED***')
   ```

3. 清理后**强制推送**,并通知所有协作者**重新克隆** —— 否则别人一 push 就把旧对象带回来了。
4. 如果曾推到过公开平台,还要检查 fork、缓存页面、事件日志。
5. **不要**用 `git commit --amend` 或"删了再提交一次"来掩盖 —— 那只会多留一条痕迹。

## 容易踩的坑

- **浅克隆没有历史。** `--depth=1` 或者 CI 里的默认 checkout,历史是空的,扫不出东西。让用户完整克隆后再扫。
- **stash 和 reflog 也在对象库里。** `--dangling` 能覆盖一部分。
- **删大文件不会缩小仓库。** 历史里的 blob 还在,得 `filter-repo` 才能真正清掉。
- **GPG 签名。** 清理历史会让已有签名失效,提前跟用户说明。
- **不是 git 仓库。** 目录里没有 `.git` 时脚本直接报错退出 —— 先确认目标对不对。
- **别把历史命中和当前命中等同。** 报告里要分清"当前代码里就有"和"只在历史里有",处置方式不同。
