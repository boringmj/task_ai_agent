# 维度判据

七个维度各自的信号、定级思路、以及**什么情况不算问题**。脚本只能圈候选,结论靠这里的判断。

**一条通用前提**:判断之前先看这段代码的性质。**生成代码、第三方 vendored 代码、文档与示例里的代码、测试夹具本身**一律不进正文 —— 它们要么不该改,要么改了也会被下次生成覆盖。

## 1. 函数规模

### 信号

- 函数体过长(经验阈值 50 行左右,随语言浮动)
- 嵌套过深(经验阈值 3~4 层)
- 分支过多(近似圈复杂度 > 10)
- 参数过多(超过 4~5 个)

### 怎么判

- 关键**不是数字,是"它做了几件事"**。一个 80 行、只做一件事的解析器不算问题;一个 30 行却把 IO、校验、业务、日志揉在一起的函数才是。
- 深嵌套往往是「没有早返回」的信号 —— 用 guard clause 把异常路径提前 return 掉,深度通常立刻下降。
- 参数多通常意味着缺一个参数对象,或这个函数该拆。

**不算问题**:生成代码、长常量/数据表、单一切换分发(大 switch)、测试函数。

**语言信号**:Python 用 `radon` 量圈复杂度、`ast` 数嵌套;JS/TS 看 `eslint` 的 `complexity` / `max-depth`;Go 用 `gocyclo`(但 Go 惯用多返回值,参数多不一定坏)。

## 2. 命名与可读性

### 信号

- 单字母或无意义命名(循环下标 `i`/`j`、lambda 参数、数学惯例除外)
- 名实不符(叫 `get_user` 却写库)
- 魔法数字 / 魔法字符串(未提取常量)
- 注释与代码矛盾、注释掉的死代码

### 怎么判

- 命名问题几乎都是 **L1**,除非它导致**误用**(叫 `get_` 却修改状态 → 抬到 L2/L3)。
- 魔法数字:同一个值在**多处**出现且含义相同 → 该提常量;只出现一次、语义自明的 `3` 不必动。
- **撒谎的注释比没有注释更糟** —— 它会让后来者相信错的。

**不算问题**:需要领域知识才觉得"不达意"的术语、团队既定缩写;以及**格式化工具管辖的范围**(引号、行宽、缩进)—— 那些交给 formatter,不要进正文。

## 3. 错误处理

这是最容易出缺陷的维度,权重最高。

### 信号

- 静默吞掉:`except: pass`、`except Exception: pass`、`catch (e) {}`
- 捕获过宽:裸 `except:`、`except BaseException`、`catch (Throwable)`
- 捕获后只打日志或只 print,不处理、不重抛
- 忽略返回的错误码 / `err`
- 用异常做正常控制流
- 丢失上下文:`raise X` 不带原因、不 `from e`

### 怎么判

- **吞异常 → 至少 L3**。若吞的是关键路径(支付、数据写入、鉴权),或吞掉之后**继续写数据 / 改状态** → **L4**。
- 捕获后**确有处理**(回滚、返回错误、重试、转成领域异常)→ 降到 L2。
- 有注释写明**故意忽略**的(如 `except FileNotFoundError: pass  # 首次运行`)→ 降到 L1。

```python
# L3:静默吞掉,调用方以为成功
try:
    write_record(row)
except Exception:
    pass

# L1:明确说明意图的忽略
try:
    cfg = open(path).read()
except FileNotFoundError:
    cfg = DEFAULT  # 首次运行,正常
```

**不算问题**:顶层兜底捕获(记录后退出)、测试里的异常断言、明确 best-effort 的清理(关不掉就算了)。

## 4. 资源管理

### 信号

- 文件 / 连接 / socket / 锁 / 子进程 打开后未关闭
- 关闭动作不在 `finally` / `with` / `using` / `defer` 里
- 异常路径漏释放(开 → 用 → 关,中间一抛就漏)
- 锁 acquire 后异常路径不 release
- 线程 / 协程创建了不 join / await
- 临时文件、临时目录不清理

### 怎么判

- 长驻服务里的资源泄漏 → **L4**;一次性脚本里 → L2 甚至 L1,按影响面定。
- 语言本有惯用法(`with` / `using` / `defer` / RAII)却没用来兜底 → 基本可判定是疏漏,而不是有意为之。

**不算问题**:进程生命周期内一直存活的全局连接(如 Web 框架的连接池),由框架管理。

## 5. 重复代码

### 信号

- 成段复制(经验阈值 10 行以上几乎相同)
- 近似分支(同一段 `if`/`else` 两支只差一处)
- 同一业务规则散落在多处

### 怎么判

- 唯一标准是「**未来会不会一起改**」。会一起变的重复(业务规则、格式约定)是真问题;只是碰巧像、而业务上注定分化的两段,抽出来反而有害 —— **过早抽象比重复更难收拾**。
- 最有力的论据是「**改一处就得记得改另外三处**」,报告里就这么写。
- 三行相似不算;三十行几乎一样才算。

**不算问题**:测试用例之间的相似(可读性优先于 DRY)、生成代码与模板、不同模块各自实现同一算法而耦合成本高于收益。

## 6. 类型安全

### 信号

- 动态语言里关键路径缺类型标注
- `Any` / `any` / `interface{}` 泛滥
- 类型断言 / 强转未做校验(空值风险)
- 用字符串当枚举 / 状态机
- 标注与运行时行为不符(标了却在运行时传 `None`)

### 怎么判

- 类型**缺失**本身多为 L2,除非落在对外接口上。
- **骗人的类型标注**(与实际不符)→ L3。
- `Any` 泛滥看范围:局限在内部辅助函数可接受,渗进公共 API 则 L2/L3。

**不算问题**:动态语言的惯用写法、鸭子类型的小工具、生成代码。

## 7. 测试覆盖

### 信号

- 核心业务 / 关键路径没有任何测试
- 异常分支、边界条件无测试
- 断言空洞:只断言"没抛异常"或 `is not None`
- 测试依赖外部状态、结果不稳定(flaky)
- 覆盖率报告暴露的未覆盖空洞

### 怎么判

- 本技能**只报缺口,不写测试**(写测试是另一件事)。
- 未覆盖的**复杂或核心**代码 → L2/L3;未覆盖的 getter、数据类 → 不算。
- **假测试与没测等价** —— 空洞断言、只跑不验,照 L2 报。

**不算问题**:一次性脚本、原型、生成代码不需要测试。
