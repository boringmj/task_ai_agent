# 代码质量检查

对一段代码、一批文件或一个仓库做**微观质量体检**,回答三个问题:「**哪里写得不好**」「**为什么这是问题**」「**先改哪个**」。

它**不给质量总分** —— 分数没有行动价值,还会掩盖真正的热点。产出是一份**带证据的清单**:每条问题配 `文件:行号`、等级(L0~L4),以及"在这个上下文里为什么算问题"。

## 边界:只管"单个文件/函数写得怎么样"

| 问题 | 归属 |
| --- | --- |
| 这段代码写得好不好 | **本技能** |
| 有没有安全漏洞、能不能被利用 | `repo-security-audit` |
| 有没有恶意行为 | `code-risk-check` |
| 模块 / 目录怎么组织、依赖方向对不对 | `repo-structure-analysis` |
| 该往什么目标形态重构 | `repo-architecture-design` |

明确**不做**这几件事:

- **性能剖析** —— 热点定位、算法复杂度实测,那是性能分析的活。
- **第三方依赖健康度** —— 过时、CVE、许可证。
- **找业务逻辑 bug** —— 本技能能指出「**易出错**的模式」(吞异常、可变默认参数、边界没处理),但不负责证明某段业务算错了;证明靠测试。
- **代写测试** —— 只报覆盖缺口,不产出测试代码。

## 四条铁律

1. **先扫后读。** 用脚本圈出候选,再只读命中的位置。不要为了"看看质量"把整个仓库读进上下文 —— 既慢又容易被大量无关代码淹没。
2. **没有上下文就没有结论。** 长函数、重复、短命名,在一种上下文里是问题,在另一种里是合理设计。每条结论都要能说出「在**这个**上下文里为什么是问题」;说不出就移到「待确认」,不要硬报。
3. **规则给线索,判断给结论。** 脚本的正则和阈值只负责圈候选,必然误报(测试夹具、生成的代码、恰好像的片段)。**报告里只写复核过的**,而且复核时要读上下文。
4. **分清读到的和推断的。** 「这个函数 120 行」是读到的;「它改动时大概率会漏改」是推断 —— 后者要标出来,别混成事实。

## 覆盖七个维度

| 维度 | 看什么 |
| --- | --- |
| 函数规模 | 长度、嵌套深度、分支数、参数个数 |
| 命名与可读性 | 命名是否达意、魔法数字、注释与代码是否一致 |
| 错误处理 | 吞异常、捕获过宽(`except:` / `catch (e) {}`)、忽略返回的错误码 |
| 资源管理 | 文件 / 连接 / 锁 / 子进程是否成对释放,异常路径会不会漏 |
| 重复代码 | 成段复制(改一处漏一处)、近似分支 |
| 类型安全 | 动态类型滥用、`Any` 泛滥、类型标注与运行时不符 |
| 测试覆盖 | 关键路径与异常分支有没有测(只报缺口) |

每个维度的判据、常见信号、以及「什么情况其实不算问题」见 `references/dimensions.md`。

## 质量等级与优先级

等级**不是单看模式**,而是「模式 × 这段代码的重要性」。同一个吞异常,在主流程里和在一次性脚本里不是一回事。

先按模式定**基础级**:

| 级别 | 名称 | 判据 | 典型 |
| --- | --- | --- | --- |
| L0 | 良好 | 该处没有实质质量问题 | — |
| L1 | 瑕疵 | 只影响可读性或一致性,不影响正确性,不改也能用 | 命名不达意、魔法数字、注释过时或缺失、轻微冗余 |
| L2 | 应改进 | 显著抬高维护成本、改动时容易踩坑 | 超长函数、深嵌套、参数过多、成段重复、上帝函数、类型标注缺失 |
| L3 | 高风险 | 容易制造缺陷,或让缺陷难以被发现 | 吞异常、捕获过宽、忽略错误返回、异常路径漏释放、关键逻辑复杂度失控 |
| L4 | 严重 | 已经在制造、或必然制造缺陷 | 资源泄漏、可变默认参数、静默失败导致数据丢失或状态不一致、不可达代码掩盖逻辑错误 |
| LX | 无法判定 | 上下文不足,需要人工确认 | 只看片段判断不了调用方与重要性 |

再按**代码重要性**调整:

- **上调**:核心业务路径、近期改动热区、被大量调用的工具函数、正在扩展的模块。
- **下调或标为「不建议动」**:一次性脚本、生成的代码、即将废弃的模块、测试夹具本身。

最后给出**优先级 = 等级 × 重要性 ÷ 改动成本**,并按它排序。报告里把结论分三档写清:**现在改**(L3 及以上)/ **排期**(L2)/ **不建议动**(L1,以及经重要性下调后的条目)。

## 流程

### 1. 确认范围与目的

先弄清要评什么:整个仓库、某个目录、还是几段代码。再问一句(或从上下文判断)用户在意的是「全面体检」还是「某块代码要动手改前的把关」—— 前者按维度铺开,后者只盯相关部分。

### 2. 跑扫描脚本,拿到候选

```bash
python3 /skills/code-quality-check/scripts/quality_scan.py <目标路径> --json quality-<目标名>.json
```

输出 JSON:按维度和预估等级分组的候选命中,每条带文件、行号、代码片段与度量值。**先只看汇总**,不要在这一步读源码。

脚本用 AST 对 **Python** 精确度量函数规模与吞异常;其它语言目前只覆盖空 catch、重复块与少数通用信号 —— 函数规模一类的度量要人工看,或借助该语言现成的工具(`radon` / `eslint` / `gocyclo`)。

### 3. 复核每一条候选

对命中项逐个读上下文,做三件事:

- **剔误报** —— 是不是测试、生成代码、字符串/注释里的示例。
- **判真伪** —— 这个模式在这里真的构成问题吗?对照 `references/dimensions.md` 的「不算问题的情况」。
- **补上下文** —— 这段代码重要吗?被谁调用?近期改过吗?这一步决定最终等级。

### 4. 定级与排序

按上面的规则给每条定级,再用重要性调整,填进三档结论。**不要为了凑数把 L1 的东西也塞进正文** —— 它们归到报告的附录里。

### 5. 出报告

按 `references/report-template.md` 的结构写,存到工作区,默认文件名 `<目标名>-代码质量.md`。

- 每条结论**都要能落到具体位置**,不要写「整体可读性一般」这类无法行动的判断。
- 报告开头给一页「结论摘要」:一共几处、几处 L3 及以上、最该先动的两三处。
- 结尾写「未覆盖范围与待确认」,把没看的部分和把握不大的判断交代清楚。

## 容易踩的坑

- **把风格问题当质量缺陷。** 缩进、引号、行宽这类交给格式化工具,除非项目明确要求,不要进正文。
- **顺手重构。** 本技能只**报告**,不改代码 —— 用户没让你改就不要改;要改走 `repo-architecture-design`。
- **只报问题不给位置。** 「错误处理不规范」没有用;「`a.py:88` 的 `except Exception` 把异常吞了,且下面是空分支」才有用。
- **过度泛化。** 一个函数长就断言"整个模块难维护",一个重复就断言"架构有问题" —— 结论的范围不要超出你看到的证据。
- **拿阈值当结论。** 「超过 50 行就是坏味道」是错的;阈值只用来圈候选,判断要回到"它是不是做了多件事"。
