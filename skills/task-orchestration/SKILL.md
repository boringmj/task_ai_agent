# 任务编排

## 什么时候用

下面三条**同时满足两条以上**才值得建计划:

- 任务明显不止一步,且步骤之间有先后依赖(前一步的产出是后一步的输入)
- 每步的成果**可以被验证**(有退出码、有输出文件、有测试)
- 可能跨多轮对话才能做完,或者中途会被打断

反面清单,碰到就直接做,别建计划:

- 单步就能完成的任务
- 只是问答、查资料、看一个文件
- 需求还没定,需要先探索 —— 先探索清楚再来建计划

## 核心思想:状态必须落在文件里

这个框架的上下文是**有损**的:对话过长会自动压缩,细节被摘要替换;单轮有步数上限;会话重启只恢复对话历史,恢复不了你没写下来的东西。

所以**唯一可靠的记忆是文件**。编排的全部要点就一句话:

> 任何时候,一个不了解前情的人(或压缩后的你)只读这几个文件,就能接着把活干完。

判断标准很直接:如果你在上下文里记住了一个关键结论、却没写进文件 —— 那它就是个隐患,趁早落盘。

## 一、建计划

在工作区里建一个任务目录,名字要能认出来:

```text
plans/<任务名>/
    plan.md          计划树(唯一权威来源)
    journal.md       执行日志:每步做了什么、结果、意外
    steps/           每个步骤的细化说明,执行到哪一步才写哪一个
        01-xxx.md
```

`plan.md` 必须机器可读,所以用固定小节和字段,不要自由发挥。骨架如下(完整模板见 `assets/plan-template.md`):

````markdown
# 计划:<任务名>

- 目标: <一句话,可验收的整体目标>
- 完成标准: <整体做完的标志,同样要可机检>
- 建计划时间: <YYYY-MM-DD HH:MM>

## 步骤

### S1 抓取原始数据

- 依赖: 无
- 状态: todo
- 验收: `python scripts/fetch.py` 退出码为 0,且 data/raw.csv 行数大于 0
- 产出: data/raw.csv

### S2 清洗并入库

- 依赖: S1
- 状态: todo
- 验收: `pytest tests/test_clean.py` 全部通过
- 产出: db/clean.sqlite

## 阻塞与问题

## 决策记录
````

字段的硬要求:

- **ID**:`S1`、`S2` 递增。一经分配**不许改** —— 依赖关系靠它引用。
- **依赖**:前置步骤的 ID,多个用逗号分隔;没有就写「无」。
- **状态**:只能是 `todo` / `doing` / `done` / `blocked` 四者之一。
- **验收**:**必须可机器判定** —— 写命令与期望结果,不写「质量好」「合理」「没问题」这类判不了的词。
- **产出**:这一步会生成或修改哪些文件,没有就写「无」。

验收标准是整份计划的命门。写不出可判定的验收,说明这一步还没想清楚 —— **先想清楚再写进计划**,不要带着模糊的验收开工。

## 二、逐步执行

每一轮只处理**一个**步骤:

1. **校验并取就绪步骤** —— 跑 `scripts/validate_plan.py`,它直接告诉你当前该做哪一步。
2. **细化到 `steps/`** —— 把怎么做(命令、参数、要改的文件、预期观察)写进 `steps/NN-xxx.md`,再动手。
3. **执行** —— 具体动作交给相应工具。要跑代码或命令时,危险或不可信的一律进虚拟机,不确定的进容器,只有确认安全的才直接在宿主上跑。
4. **验收** —— 把「验收」那条命令**真的跑一遍**。跑过才算过。
5. **落盘** —— 把 `plan.md` 里这一步的状态改成 `done`,往 `journal.md` 追加一段(做了什么、结果、意外)。
6. **提交检查点** —— 用 git 存一个版本,message 写成 `[S3] 简短描述`。

### 为什么每轮只展开一个步骤

因为上下文会压缩。十个步骤的细节同时塞在上下文里,压完剩一团糊;而只留当前步骤的细节,**压缩也压不掉你正在做的事**。做完一步,细节的价值就转移到 `journal.md` 和产出物里了。

### 提交检查点

- 每步通过验收就提交一次,`[S<id>] 描述` 这种 message 便于日后对账。
- 想回退就用 `git restore` 或 `git checkout <版本> -- <路径>` 恢复文件,**别用 `reset --hard`** —— 它会连历史一起抹掉,而且需要用户确认。
- 提交前先 `git status` 看一眼,别把临时文件或凭据一起提交进去。

## 三、失败与阻塞

- 同一验收**最多重试 2 次**,且每次**必须换一种做法**(换假设、换参数、换思路)。重复跑同一条失败的命令不叫重试,叫浪费。
- 两次都不过:状态改成 `blocked`,在「阻塞与问题」里写清 **卡在哪、已试过什么、需要什么才能推进**,然后**停下来问用户**。
- 绝对不要为了前进而做这三件事:
  - 放宽或改写验收标准
  - 跳过失败的步骤先做后面的
  - 把「没验证」当成「应该没问题」

计划可以调整,但**调整要写进「决策记录」并告知用户** —— 静默改计划比失败更糟。

## 四、必须停下来问用户的时刻

碰到这些,不要自己拍板:

- 计划涉及**破坏性操作**:删除、覆盖、批量改写、`reset` 之类
- 要改**验收标准**或整体目标
- 发现任务的**前提是错的**(要改的文件不存在、接口签名和描述不符)
- 有步骤 `blocked`,或同一处连续失败
- 改动范围**超出计划**(顺手又想改点别的)

## 五、断点续做

重新接手一个任务时(换了会话、上下文被压缩、隔了几天),**不要凭记忆**,按这四步走:

1. 读 `plan.md` —— 目标和完成标准还在不在?
2. 跑校验脚本 —— 当前就绪的步骤是哪个?
3. 读 `journal.md` 最后几段 —— 上一步实际做到哪、有没有留下没处理的问题?
4. 读 `steps/` 里最后那个文件 —— 有没有半途而废的动作需要先收拾?

走完再动手。**先确认现状,再谈推进** —— 很多「接着做」翻车,都是因为跳过这步,把做完的事又做一遍,或者覆盖了比记忆更新的产出。

## 六、收尾

全部步骤 `done` 之后:

1. 跑一遍整体「完成标准」,确认真的达成
2. 归置交付物(工作区有 `reports/` 归档约定的,产出放 `reports/<任务名>/`)
3. `journal.md` 补一段总结:做了什么、留下什么、还有什么没做
4. 最后提交一次
5. 向用户汇报:**做了什么 → 结果(带证据) → 没做或做不到的 → 建议的下一步**

## 易踩的坑

- **计划太大** —— 一个步骤超过一轮能做完的量就再拆。步骤粒度是「一次能验证完」。
- **验收写成愿望** —— 「代码整洁」判不了,「`ruff check` 无告警」判得了。写不出可判定的验收,就是没想清楚。
- **忘记落盘** —— 上下文里的进展不算数。做完一步没写进文件,压缩后等于没做。
- **一次想改整条链** —— 改着改着范围失控。发现范围要变,先停下记录、再问用户。
- **journal 写成流水账** —— 它的读者是「压缩后的你」,需要的是结论与遗留问题,不是每条命令的复述。

## 附带资源

- `scripts/validate_plan.py` —— 校验计划:ID 唯一、依赖存在、依赖图无环、验收非空、状态合法,并算出当前就绪的步骤。每次执行前跑它,别靠肉眼。
- `assets/plan-template.md` —— 计划文件模板,复制后填空。
- `references/patterns.md` —— 常见任务类型的分解套路:数据管道、重构、迁移、批量整改。

上面这些路径都**相对技能目录**(技能在容器里只读挂载,实际位置见加载时给的资源清单);
而计划文件在**工作区**里,(`plans/...`) —— 两者不是一回事,别混。
