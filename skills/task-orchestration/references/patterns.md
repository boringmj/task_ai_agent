# 常见任务的分解套路

按任务形态挑一个骨架,改成本任务的步骤。骨架不是圣旨 —— 但**每步都要有可判定的验收**这条不能省。

## 通用:步骤粒度

一个步骤 = **一轮内能做完、且做完能验证**的量。

- 太粗(「实现后端」)→ 做不完、验不了,一卡就全卡住
- 太细(「打开文件」「加一行 import」)→ 计划文件本身成了负担

判断办法:如果你没法为这步写出一条能跑出 0/1 的验收命令,它就是太粗或没想清楚。

## 数据管道

```text
抓取 → 清洗 → 校验 → 入库 → 抽样复检
```

- 抓取:验收看**产出存在且非空**(行数 > 0、字节数 > 0)
- 清洗:验收看**断言**(空值率、去重后行数、字段类型)
- 校验:验收看**校验脚本退出码**,而不是人工看一眼
- 入库:验收看**查询能取到预期条数**

## 重构

```text
固定行为(加测试/存基线) → 小步改 → 每步跑测试 → 收尾清理
```

关键是**第一步先造出"能证明没改坏"的东西** —— 测试、快照、或改动前的输出留样。没有这个就动手改,后面无法判断是否改坏了,只能靠感觉。

每步的验收就是「测试全绿 + 基线输出比对一致」。

## 迁移(数据库、API、目录结构)

```text
盘点现状 → 试点一个 → 批量迁移 → 全量校验 → 清理旧路径
```

- 盘点要产出**清单文件**(迁移对象的完整列表),它是后续所有步骤的输入
- 试点一个:验证方案可行,验收是**那一个对象迁移成功且校验通过**
- 批量:验收是**数量对得上**(迁移数 == 清单数)
- 清理旧路径放最后,且**属于破坏性操作 —— 动手前必须问用户**

## 批量整改

```text
抽样定规则 → 写脚本 → 干跑(dry run) → 全量执行 → 抽查
```

干跑那一步不能省:它先输出「将会改动哪些文件、怎么改」而不真的改。验收就是**干跑结果与预期一致**。

## 需求还没定的时候

不要急着建完整计划。先建一个**探索步骤**,它的产出是一份结论文档(现状、可选方案、推荐),再据此建后续计划。

探索步骤的验收就是「结论文档写到约定路径,且回答了几个明确问题」。

## 验收写法对照

| 差的写法 | 好的写法 |
| --- | --- |
| 代码整洁 | `ruff check .` 无告警 |
| 测试通过 | `pytest tests/ -q` 退出码 0 |
| 数据处理正确 | 输出行数 == 输入行数 - 去重数,且无空 id |
| 接口可用 | `curl -s -o /dev/null -w '%{http_code}' ...` 返回 200 |
| 文档写好 | `reports/x.md` 存在,且含「结论」「证据」「未覆盖」三个小节 |
| 性能提升 | 基准脚本输出 < 改动前的 80% |

## 什么时候该停下来重规划

- 某步的验收连续两次不过 —— 多半是**前面某步的假设错了**,回去看,别硬顶
- 发现计划里的步骤依赖实际不存在(接口签名不符、文件不在)
- 范围膨胀:做着做着发现要改的东西远超预期

这三种情况都属于「前提变了」,按技能正文的规矩:记进「决策记录」,停下来问用户。
