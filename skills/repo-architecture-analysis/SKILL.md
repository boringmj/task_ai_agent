# 仓库架构分析

输入通常是一个或多个工作区里的代码仓库,产出是一份**结构化的架构分析报告**:技术栈、目录职责、模块依赖、核心流程、架构模式与风险点。

## 三条铁律

1. **不要通读仓库。** 先用脚本扫出全局结构,再按需读少数关键文件。把整个仓库读进上下文既慢又容易撑爆。
2. **重活交给脚本。** 统计和依赖抽取用 `scripts/scan_repo.py` 在容器里跑,它只回汇总结果。
3. **注意路径换算。** 文件工具返回的是宿主路径(`D:\...\workspace\clones\foo`),
   容器里必须写成 `/workspace/clones/foo`;照抄宿主路径会 `FileNotFoundError`。

## 步骤

### 1. 找到并确认仓库

- 外部仓库一般克隆在 `clones/` 下(`git clone <url> clones/<名字>`)。
  先 `list_files` 看根目录,再读 `README*` 弄清它是干什么的。
- **多个仓库**时:先各自独立分析,最后再补一节仓库之间的关系。
- **大型 monorepo** 要先识别出各个子包/子应用,逐个拆开看。

### 2. 跑扫描脚本,拿到全局图景

```bash
python /skills/repo-architecture-analysis/scripts/scan_repo.py /workspace/clones/<名字>
```

输出一份 JSON:目录树、语言统计、构建/依赖清单文件、入口候选、最大的文件与目录、近似依赖边。
**先只看这份汇总**,这一步不要读源码。

### 3. 只读少数关键文件

按脚本给的线索,用 `read_file` 挑着读:

- **依赖清单**(`package.json` / `pyproject.toml` / `go.mod` / `Cargo.toml` /
  `pom.xml` …)→ 技术栈、第三方依赖、启停脚本。
- **入口文件**(`main` / `index` / `app` / `cmd/`)→ 程序怎么启动、装配了哪些东西。
- **被依赖最多、体量最大的几个模块** → 主要职责。
- **配置**(`settings*` / `config*` / `.env.example`)→ 运行期依赖与开关。

### 4. 理清依赖与数据流

- 结合脚本的依赖边,并用 `grep_files` 抽查关键 import,确认模块依赖方向。
- 留意:循环依赖、层次倒挂(底层反过来依赖上层)、被大量引用的「上帝模块」。
- 从入口出发追**一条主流程**:请求/命令进来 → 经过哪些模块 → 落到哪里。

### 5. 识别架构模式

对照 `references/architecture-patterns.md`,判断它接近哪类模式(分层 / 六边形 / 插件化 /
事件驱动 / MVC …),以及哪里偏离了该模式。

### 6. 产出报告

按 `references/report-template.md` 的结构写,存到工作区,文件名 `<仓库名>-architecture.md`。

- **每个结论都要有依据**(点明哪个文件、哪一行或哪段代码),不要空泛断言。
- 依赖关系用 mermaid 图表达,直接在报告里放代码块。
- 结尾写「待确认」:你没能从代码看清的地方列出来,交给用户补。

## 分析多个仓库时

- 先各自产出单仓报告,再补一节「仓库间关系」:谁依赖谁、通过什么接口通信(HTTP / RPC / 共享库 / 数据库)。
- 可对根目录再跑一次脚本,看整体布局。

## 容易踩的坑

- **分清「读到的」和「推断的」**,推断必须标注出来。
- **不要为了凑齐报告结构去猜**;看不清就写进「待确认」。
- 生成物(依赖锁、构建产物、日志)不要当作源码分析——脚本已默认跳过常见目录,但你自己读文件时也要注意。
- 脚本给的是**近似**依赖(静态抽取),动态导入、反射、字符串拼出的模块名它抓不到,结论要留有余地。
